FAQ

UniBasic Migration Questions Enterprises Ask Us

What is UniBasic, and why migrate it to Java?

UniBasic is the BASIC-derived programming language used in Rocket UniData and UniVerse MultiValue systems. Most UniBasic applications were written in the 1980s and 1990s and still run core business processes. Migrating UniBasic to Java removes dependence on a shrinking pool of MultiValue developers, eliminates UniData license fees, and moves your application onto a platform with a large, current talent market and modern tooling.

How does automated UniBasic to Java migration work?

Our platform parses every UniBasic program, subroutine, and dictionary in your UniData estate and generates equivalent Java, while MultiValue files are mapped to a normalized SQL schema. Each converted program is then run against recorded production inputs to prove functional equivalence with the original UniBasic. The result is a UniBasic migration that is fast, repeatable, and verified rather than hand-rewritten.

Will the converted Java code actually be maintainable?

Yes. To be transparent: transpiled code is not fully idiomatic Java, since it retains some structure from the original UniBasic. But it is well-organized, readable, and thoroughly manageable, not machine-generated spaghetti or a runtime emulator. Any Java developer can read, test, and extend it, and it can be refactored incrementally over time. We include documentation and knowledge transfer so your team is productive immediately.

How do you handle the MultiValue database?

UniData files, dictionaries, and multivalued fields are mapped to a normalized relational schema. Data is migrated with automated validation, and you choose the target SQL database: PostgreSQL, Oracle, SQL Server, or another engine that fits your standards.

What about the 5% that isn't converted automatically?

Complex or ambiguous constructs are flagged by the platform and handled by our migration engineers. Every manually-touched program goes through the same functional equivalence testing as automated conversions.

What about phantom (batch) jobs?

They're part of the migration, not an afterthought. Phantom processes become scheduled Java services, and the assessment phase inventories them along with the rest of your estate so nothing is missed.

How long does a migration take?

It depends on codebase size and complexity, but automation compresses timelines from years to months. The assessment phase gives you a concrete, evidence-based estimate before you commit.

Can we keep operating during the migration?

Yes. Your production system runs untouched while we convert and validate. Cutover is phased, with parallel running and rollback options, so business continuity is protected throughout.
